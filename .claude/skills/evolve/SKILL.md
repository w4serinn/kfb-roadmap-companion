# evolve: kfb-roadmap-companion 自動開発サイクル

以下の手順で **1周だけ** 実行してください。
1周 = 「docs/ROADMAP.md から次に対応する単位(意味のある塊)を選ぶ → 実装 → テスト →
コードレビュー → ドキュメント更新 → commit → push → バックログ更新」です。

このプロジェクトは、Kawaii Future Bass作曲学習ロードマップ(1年計画)を実際に
走り切るための支援サイトです。音楽制作アプリではなく、継続と理解の橋渡し役である
ことを常に意識してください。

---

## 0. 事前チェック

- 作業ブランチは必ず `evolve/cycle-<連番>`。mainにいたら最新化してブランチを作る。
  人間がmainに取り込むまでは、同じ`evolve/cycle-<連番>`ブランチに複数サイクル分の
  コミットが積み重なるのが正常な動作である。
- サイクル開始時に `git fetch origin` を実行し、現在のブランチの最新コミットが
  すでに `origin/main` に取り込まれているか確認する。取り込まれていれば、
  `git switch main && git pull` で最新化し、新しい `evolve/cycle-<連番+1>`
  ブランチを作り直してから、通常の手順(1節以降)に進む。
- 前回サイクルが未完了(実装済みだがテスト未了、`partial`のまま等)の形跡があれば、
  新しいタスクに着手せず続きから再開する。
- ユーザーの手作業らしき変更が混ざっていたら、何もせず報告して終了する。
- `docs/ROADMAP.md` の「プロジェクトの目的」「非ゴール」セクションを必ず確認し、
  そこから外れた実装をしないこと(特に「音楽制作アプリの代替にしない」
  「他者比較・SNS共有機能を作らない」の2点は方針として確定済み)。

## 提案の姿勢

新機能・メッセージ文言・音源プリセットの3つの提案チャネル(下記参照)は、
実装に詰まった時だけの避難先ではない。「これがあれば継続の助けになる」と
感じたら、詰まっていなくても軽い気持ちで提案してよい。ただし1サイクルにつき
提案は目安として1件までとし、選んだタスクの実装を差し置いて提案作業そのものに
時間をかけすぎないこと。

## 1. タスク選定

`docs/ROADMAP.md` を以下の優先順で読み、次に対応するタスクを選ぶ。

1. 「バグ修正(最優先)」セクションの未対応項目
2. 現在のフェーズで進行中の機能の未完了サブタスク(上から順)
3. 現在のフェーズで未着手の機能の最初のサブタスク
4. 上記が全て`blocked`/承認待ちで進められない場合のみ、次フェーズの機能に
   前倒しで着手してよい(ただしフェーズの優先順位は`docs/ROADMAP.md`の
   「フェーズ」セクションに従う)

- 選んだ候補が `blocked` または承認待ちで今は着手できない状態の場合、
  そのタスクは一旦スキップし、次の候補に進む。依存が解消されたことを
  確認できたら、そのサイクルで再訪してよい。
- **サイズLの項目には着手しない**。S/Mの子項目に分割してROADMAPを書き換えるだけで
  1サイクルとしてよい。
- **1サイクル=1つの、意味的にまとまった単位**とする。関連性が強い場合、または
  無関係でもAPI使用量を抑える目的で、目安2〜3項目をまとめてよい。まとめる場合も
  コミットの差分は項目ごとに分かりやすく分離して書くこと。
- ROADMAPのタスクが尽きたら、既存の実装を見て新しいタスク案を3〜5個
  「今後のタスク候補」に追加し、その中から1つ着手する。

## 2. 実装(技術方針)

- **ロジックとUIの分離**: 音の生成(コード/リズムのシンセ処理)、進捗判定
  (最終操作日からの経過日数、バージョン番号の発行など)は、DOM操作と混在させず
  純粋関数として実装する。目安のファイル配置:
  - `assets/audio-engine.js` — Web Audio APIによるコード/リズム生成ロジック
  - `assets/progress-logic.js` — 経過日数判定・完了率計算・バージョン番号発行等
  これらはテスト対象になるため、DOM(`document`, `window.localStorage`直接参照)
  を関数内に埋め込まず、必要な値は引数で受け取り、結果を返すだけの形にする。
- **データ保存**: `localStorage`のキーは必ず `kfb-` プレフィックスを付ける
  (例: `kfb-progress`, `kfb-last-active-date`)。他のアーティファクト等との
  混在を避けるため。
- **日付ロジックのテスト容易性**: 「最終操作日から7日空いたら復帰表示に切り替える」
  のような日付比較は、`Date.now()`を関数内で直接呼ばず、現在時刻を引数として
  渡せる形にする(テストで日付をモックできるようにするため)。
- **音源プリセットの追加**: 新しいコード種別・リズムパターンを追加したい場合、
  実装前に `docs/SOUND_PRESETS.md` の「依頼中」に用途・音の特徴・参考音源
  (あれば)を追記し、承認を待つ。承認前に実装で使わないこと。
- **メッセージ文言の追加**: 「今日は開くだけでOK」「ベース音1音取れれば合格」
  のような励まし・合格ライン系の文言を新規に追加したい場合、実装前に
  `docs/MESSAGES.md` の「提案中」にトーン・使用箇所を追記し、承認を待つ。
  既存の`docs/MESSAGES.md`「承認済み」からの文言をそのまま使う場合は
  承認不要。
- **フェーズを超えた機能の先取り実装をしない**: 現在のフェーズ外の機能
  (例: フェーズ1作業中に耳コピ支援ツールを実装する等)に着手したくなった場合、
  実装せず `docs/FEATURE_PROPOSALS.md` に提案として追記するだけにする。

### タスク実行中にスコープが大きすぎると判明した場合

見積もり(S/M)を超えて作業が拡大しそうだと判明した場合、そのまま続けず以下を行う。

1. その時点で完結し、テストが通る最小の成果があれば、それだけを今回のコミット対象とする
2. 残りの作業を `docs/ROADMAP.md` の新しい子タスクとして書き出す(サイズを再見積もりする)
3. 該当タスクの status を `partial` にして理由を記載し、サイクルを終える
4. 完結した成果が無い場合は、変更を `git stash` で退避し、`blocked` と同様の扱いとする

## 3. テスト・lint

プロジェクトに設定されたコマンド(例: `npm run lint` / `npm run test` /
`npm run build` 等、`package.json`に準拠)を順に実行し、**全て成功させてから
コミットする**。

失敗したら修正して再実行。**2回連続で同じ原因で失敗して解決の目処が立たない場合**は:

- 変更を `git stash` で退避
- `docs/ROADMAP.md` の該当項目を `blocked` にして理由を記載
- そのことだけをコミットしてサイクルを終える

## 4. コードレビュー

テストが通ったら、`local-review` skillを実行し、まだcommitしていない差分
(ワーキングツリー・新規ファイル含む)を客観的にレビューする。

指摘への対応方針:

- 今回の変更が原因の不具合 → その場で修正し、テスト一式を再実行してから同じコミットに含める
- スコープ外・既存の別問題・優先度の低い改善 → 直さず `docs/ROADMAP.md` にtodoとして追記する
- 誤検知・対応不要 → 対応せず、サイクル終了時の報告でその旨に触れる

`local-review` が使えない場合はレビューをスキップし、サイクルは止めない。

## 5. ドキュメント更新

- 変更内容に応じて `README.md` を同一サイクルで更新する
- サブタスクを `[x]` にした際は、そのサブタスク行を `docs/ROADMAP.md` から
  `docs/roadmap-done.md` の対応する機能見出し欄へその場で退避する。
  この運用により `docs/ROADMAP.md` は常に「見出し・注記・未完了サブタスクのみ」の
  軽量な状態を保つ。
- ある機能のサブタスクが全て完了した場合、該当機能の status を `完了` にする。
- **`完了`機能への新規タスク追加時は status を `進行中` に戻す**。`完了`は
  「その機能に未完了のタスクが一つも無い」ことを表すラベルであり、新規タスクを
  抱えたまま`完了`表示を続けてはならない。

## 6. コミット・プッシュ

- 1サイクルの成果を必ず1コミットにまとめ、`evolve/cycle-<連番>` ブランチにpushする
- コミットメッセージ形式: `feat: <内容>` / `fix: <内容>` / `docs: <内容>`

## 7. バックログ更新・サイクル終了報告

- 今回選ばなかったタスク、新たに見つけた改善点を`docs/ROADMAP.md`に反映する
- 以下の内容を `docs/cycle-log.md` に追記する:

```
## YYYY-MM-DD HH:MM
- 実装: (実装した内容)
- レビュー: OK / 指摘N件対応 / スキップ
- lint: ✓ / test: ✓ / build: ✓
- 次回予定: (次のサイクルで着手予定の項目)
- blocked / partial: なし or (内容)
```

追記後、同じ内容をターミナルにも表示する。

## 禁止事項

- mainへの直接commit/push/merge(取り込みは人間がレビュー後に行う)
- PRの作成・マージ(`gh pr create`、`gh pr merge`等)を自分で実行すること。
  取り込みの判断と実行は必ず人間が行う
- 履歴改変(`rebase -i`、force push、`reset --hard`) — evolveブランチ上でも禁止
- テストが通っていない状態でのcommit/push
- ROADMAPにない大規模リファクタリング
- 承認前のメッセージ文言・音源プリセットを実装に使うこと
- 現在フェーズ外の機能の実装(提案は可、実装は不可)
- 音楽制作機能そのもの(DAW的な波形編集・録音機能等)の実装。このアプリは
  あくまで支援ツールであり、FL Studio/Vitalの代替を目指さない
- AIによるメロディー・楽曲の自動生成機能の実装。レイヤー4(メロディー起こし
  支援)は本人が思いついたメロディーの採譜支援に限定し、AIが代わりに
  メロディーを作る機能を追加しないこと。ただしレイヤー5(コード候補提示)は
  例外で、ダイアトニックコードとの構成音一致という決定論的ロジックに限り
  実装してよい。候補は必ず複数提示し、単一の正解を返す実装にしないこと
