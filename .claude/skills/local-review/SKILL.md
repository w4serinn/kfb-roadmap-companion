# local-review: ワーキングツリー差分の客観レビュー

まだcommitしていない差分(ステージ済み・未ステージ・新規ファイル含む)を対象に、
実装した視点から離れて、客観的なコードレビューを行ってください。

## 観点

- 今回の変更が原因で発生した不具合(表示崩れ、JSエラー、アクセシビリティ低下など)
- 既存の見た目・機能への意図しない影響
- **音楽制作アプリ化していないか**: このアプリは学習の継続を支援するツールであり、
  DAW的な波形編集・録音・音源ファイル管理などを実装していないか(実装してしまって
  いたら、非ゴールからの逸脱として指摘する)。ただしレイヤー5(コード候補提示)は
  ダイアトニックコードとの構成音一致という決定論的ロジックに限り許容する。
  候補が複数提示されず単一の正解を返す実装になっていたら、これも逸脱として指摘する
- **他者比較・SNS共有機能が入り込んでいないか**: 「比較対象は先週の自分だけ」という
  方針に反する、他ユーザーとの比較・ランキング・共有機能が実装されていないか
- ロジック(音生成・進捗判定)がDOM操作と混在せず、`assets/audio-engine.js`や
  `assets/progress-logic.js`のような純粋関数として分離されているか
- 日付を使う判定ロジックが、現在時刻を直接呼ばずテスト可能な形になっているか
- `localStorage`のキーに `kfb-` プレフィックスが付いているか
- 未承認のメッセージ文言(`docs/MESSAGES.md`の「承認済み」に無いもの)が
  実装で使われていないか
- 未承認の音源プリセット(`docs/SOUND_PRESETS.md`の「承認済み」に無いもの)が
  実装で使われていないか
- 現在のフェーズ外の機能に着手していないか(`docs/ROADMAP.md`のフェーズ定義を確認)
- テストでは検出できない「使い勝手」の違和感(操作導線、文言のわかりにくさ、
  合格ラインの表示が分かりにくい等)
- 挫折対策の仕組み(復帰表示・合格ライン表示・バージョン番号)が、機能追加によって
  意図せず弱められていないか

## 出力形式

指摘事項ごとに以下を出力すること:

- ID(例: A-1, B-1)
- 重要度(high/medium/low)
- 内容
- 今回の変更が原因か、既存の別問題か

## 分類の目安

- 今回の変更が原因の重大な不具合 → 呼び出し元(evolveサイクル)がその場で修正
- スコープ外・既存の別問題 → `docs/ROADMAP.md` へtodo追記対象として報告
- 誤検知・対応不要 → その旨を明記

### 非ゴール逸脱を見つけた場合の具体的な対応

これは「今回の変更が原因の不具合」として扱い、その場で以下の手順で修正すること。

1. 逸脱している実装(音楽制作機能・比較機能等)をコミット対象から外す
   (削除、またはstashする)
2. その機能で実現しようとしていた体験を`docs/FEATURE_PROPOSALS.md`に
   提案として書く(何を、なぜ必要だと感じたか)。ただし非ゴールに明確に
   反する提案(音楽制作機能の代替・他者比較機能)は提案自体を控え、
   このサイクルの報告でその旨に触れるのみとする
3. 元のタスクは、非ゴールに反しない範囲で実装し直す。収まらない場合は、
   そのタスク自体を`partial`にして理由を記載する

### 未承認の文言・音源プリセットが使われている場合の具体的な対応

これも「今回の変更が原因の不具合」として扱い、その場で以下の手順で修正すること。

1. 該当箇所を特定し、`docs/MESSAGES.md`または`docs/SOUND_PRESETS.md`の
   「提案中」に追記する(承認待ちの状態にする)
2. 実装側は、承認済みの既存文言・音源に一旦差し替えるか、プレースホルダーとする
3. 追記後、同じコミットに含める
